PARSER TOWN / ACCURACY NOTES

        
Three entrances, one shared middle

        

          This is the driver’s command parsing system. Native patterns (add_rule
          / parse_command), parser-package rules (parse_add_rule
          / parse_sentence), and DGD-style
          parse_string grammars feed one grammar engine. The native
          and package routes also share a group builder. The
          add_action compatibility adapter uses that engine too; it
          is outside the three grammar dialects explored here.
        

        

          The cart carries the selected grammar, input, token spans, chart, and
          result. Each box is one retained token; blue boxes have been scanned.
          Yard racks show actual chart-column item counts at 0.16 grid units per
          item. A loop processes the next token boundary, including the final
          column. The roads after Derivation Grove show where frontend-specific
          meaning resumes.
        

        
How much of it is real

        

          

            Computed: pattern-to-group lowering;
            group-to-grammar expansion; the printed DGD grammar subset;
            maximal-munch tokenization with rule-order ties and source spans;
            Earley prediction, scanning, completion, nullable advancement and
            item deduplication; derivation reconstruction in production order
            with longest spans first; capture extraction; noun matching against
            the example scope; and the demonstrated frontend call order. Every
            live count comes from js/model.js.
          

          

            Scaled down: two fixed lessons, one selected rule,
            two example objects, at most 120 input characters and 24 tokens. The
            browser caps work at 20,000 operations per chart or derivation pass,
            trees at 32 per span, and depth at 64. These are teaching limits,
            not driver defaults. Only the native and package capture forms
            printed in the lessons are exercised. DGD compilation accepts the
            displayed line-oriented subset and three simple regex forms.
          

          

            Assumed: the sword has id sword and adjective red;
            bob is a living with id bob. Direct and indirect checks always
            accept. Handler accepts controls the native handler’s result, the
            package’s can_ result, or the DGD accept action, which returns its
            input array or 0. All examples use case-sensitive matching. Changing
            an experiment begins a fresh run.
          

          

            Illustrated / omitted: this is JavaScript, not the
            Rust VM. Tokenization tests regexes separately instead of using a
            joint DFA; spans use JavaScript character offsets instead of UTF-8
            byte offsets. The model eagerly materializes bounded derivations and
            skips same-span cycles; Rust enumerates lazily with different
            limits. It does not implement general LPC actions, action
            memoization, the full DGD dialect, many-object selection, complete
            noun vocabulary or scope traversal, multiple-rule dispatch, caches,
            STM or I/O. Buildings, travel time, and reading stops have no
            performance meaning. Trust the demonstrated mechanism and values
            within this subset, not the animation as a benchmark.
          

        

        
Reading the tour

        

          First visits stop for 9–26 seconds, based on the explanation’s length.
          Later visits take a short beat. The default native tour takes about
          four minutes at 1×. Space holds any stop indefinitely. Next advances
          one station, including one chart column per loop. New run keeps
          reading history; Replay clears it. Reduced-motion preferences start
          the tour paused.
